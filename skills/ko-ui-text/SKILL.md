# 한국어 UI 텍스트 검수·작성

LLM이 쓴 한국어 UI 문구는 세 가지가 반복해서 무너진다. 말투가 화면마다 섞이고, 헤딩·버튼 같은 자리에 문장이 들어가고, 개발자가 자기한테 쓴 메모나 내부 용어가 그대로 화면에 남는다. 이 스킬은 그걸 진단하고 자리에 맞게 다시 쓴다.

## 언제 어떤 모드로

| 사용자 요청 | 모드 |
|---|---|
| "검수해줘", "어색한 데 찾아줘", "왜 이상한지 봐줘" | **audit**: 진단 + 수정 표 |
| "고쳐줘", "다시 써줘", "적용해줘" | **rewrite**: 진단 요약 + 파일 직접 수정 |
| "이 화면 문구 써줘", "버튼 이름 정해줘" | **write**: 규칙에 맞춰 새로 작성 |
| 모드가 불분명 | audit로 시작하고 적용 여부를 묻는다 |

파일 수정 권한이 없거나 원본이 채팅에만 있으면 rewrite도 audit 출력으로 대신한다.

## 이 스킬을 쓰지 않는 경우

화면에 보이지 않는 한국어 산문(보고, 요약, 설명, md 문서, README, 가이드, 설계 문서,
회의록)은 `ko-writing` 스킬을 쓴다. 문서는 문서체 `~한다`가 기본이라 UI 규칙과 반대다.
용어집(`ui-text.glossary.md`)은 두 스킬이 공유한다.

## 워크플로우

### 1. 맥락 확보

시작 전에 아래를 알아야 한다. 프로젝트에 `ui-text.config.md`(경로는 아래 참고)가 있으면 거기서 읽고, 없으면 대화에서 찾고, 그래도 없으면 **추정하지 말고 묻는다**. 특히 독자와 읽는 상황을 모르면 결과 전체가 어긋난다.

- 제품이 무엇인지 한 줄
- 화면 종류: 웹 / 모바일 / 키오스크 / 데스크톱 툴 / 관리자 콘솔
- 읽는 사람: 소비자 / 실무자 / 개발자 / 현장 기사
- 읽는 상황: 앉아서 정독 / 서서 흘끗 / 작업 중 곁눈질 / 장애 중 급하게
- 기본 말투: 해요체 / 합니다체 / 명사형
- 전문 용어 허용 수준

한 제품 안에서도 관리자 화면과 사용자 화면은 허용 수준이 다르다. 화면별로 독자가 갈리면 각각 명시하게 한다.

### 2. 진단

수정안을 내기 전에 `references/rules.md`의 **1. 진단 항목**을 기준으로 반복 패턴을 잡는다. 개별 문장을 나열하지 말고 유형별로 묶고, 유형마다 실제 사례 2~3개를 인용한다. 진단이 먼저인 이유는, 패턴을 안 잡고 문장 단위로 고치면 같은 문제가 다음 화면에서 또 나오기 때문이다.

### 3. 용어 확정

진단에서 "용어 흔들림"이 나왔으면 수정 전에 표기를 확정한다. 프로젝트에 용어집(`ui-text.glossary.md`)이 있으면 그걸 따르고, 없으면 이번 작업에서 확정한 표기를 용어집으로 저장하도록 제안한다. 용어집이 있어야 다음 배치에서 표기가 안 흐트러진다.

### 4. 수정 또는 작성

`references/rules.md`의 **2~5절**(역할별 기준, 말투, 금지, 판단 기준)을 적용한다. 원문이 이미 자연스러우면 손대지 않고 "유지"로 남긴다. 이 규칙이 없으면 멀쩡한 문구까지 다 바뀐다.

### 5. 출력

`assets/output-template.md` 형식을 따른다. 맥락 없이는 정할 수 없는 항목은 추측해서 고치지 말고 "결정 필요" 절에 질문으로 남긴다.

## 대용량 처리

화면이 5개를 넘거나 문자열이 100개를 넘으면 배치로 나눈다. 한 번에 다 처리하면 뒤쪽에서 용어와 말투가 흐트러진다.

1. 3~5개 화면(또는 50~80개 문자열)씩 끊는다
2. 첫 배치에서 용어집을 확정한다
3. 이후 배치는 확정된 용어집을 기준으로 "벗어난 곳만" 지적한다
4. 마지막에 전체를 한 번 훑어 배치 간 불일치를 잡는다

## 입력 형식별 처리

| 입력 | 처리 |
|---|---|
| JSX/TSX/Vue/HTML | 문자열 리터럴과 텍스트 노드만 추출. 위치는 컴포넌트명 + 줄번호 |
| i18n JSON/YAML | 키를 위치로 쓴다. 키 이름이 역할 힌트다 (`button.save`, `error.network`) |
| Figma/디자인 내보내기 | 레이어 이름을 위치로 쓴다 |
| 스크린샷 | 화면 순서 + 위치 설명 ("2번 화면 하단 버튼") |
| 붙여넣은 텍스트 | 줄번호 |

변수 삽입(`{name}`, `${count}`)이 있으면 조사 처리를 확인한다. `{name}을`은 받침에 따라 깨지므로 `{name}을(를)` 대신 문장을 조사 없이 재구성하거나, 프로젝트에 조사 처리 유틸이 있는지 묻는다.

## 프로젝트 설정 파일

프로젝트 루트 또는 `docs/` 아래에 두 파일을 둘 수 있다. 있으면 반드시 먼저 읽는다.

- `ui-text.config.md`: 1단계 맥락. 템플릿은 `assets/config-template.md`
- `ui-text.glossary.md`: 확정 용어. 템플릿은 `assets/glossary-template.md`

없으면 첫 작업 후 생성을 제안한다. 사용자가 원하면 만든다.

## 하지 말 것

- 맥락을 추정해서 진행하기. 독자를 모르면 물어라
- 진단 없이 문장 단위로 바로 고치기
- 규칙을 기계적으로 적용해서 이미 자연스러운 문구까지 바꾸기
- 프로젝트 용어집을 무시하고 "더 자연스러운" 표기로 바꾸기. 통일이 우선이다
- 수정 표 없이 파일만 조용히 바꾸기 (rewrite 모드에서도 무엇을 왜 바꿨는지 요약한다)

## 참고 파일

- `references/rules.md`: 진단 항목, 역할별 기준, 말투, 금지 목록, 판단 기준. 검수·작성 시 항상 읽는다
- `references/examples.md`: 유형별 원문→수정 예시. 판단이 애매할 때 읽는다
- `assets/output-template.md`: 출력 형식
- `assets/config-template.md`, `assets/glossary-template.md`: 프로젝트 설정 파일 템플릿
- `ko-writing` 스킬: 화면 밖 한국어 산문(보고·문서·설명). 용어집을 공유한다
