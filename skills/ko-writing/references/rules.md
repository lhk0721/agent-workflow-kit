# 한국어 문서·보고 규칙

## 1. 진단 항목

고치기 전에 아래 유형으로 반복 패턴을 잡는다. 유형마다 사례 2~3개 인용, 문제인 이유 한 줄.

### 번역투
영어 문장 구조가 그대로 남았는가.
- "~를 통해", "~에 대한", "~에 있어서", "~와 관련하여"
- "~을 제공한다", "~를 지원한다", "~을 가능하게 한다"
- 무생물 주어: "이 변경은 성능을 개선한다"
- 문장마다 붙는 "~할 수 있다"
- 영어 어순을 그대로 옮긴 긴 수식어: "앞서 언급한 세 가지 문제를 해결하기 위해 도입된 방식"
- 피동 남용: "확인되어진다", "적용되어졌다"
- "~적", "~화"의 남발: "구조적인 개선을 통한 자동화의 실현"

### AI 말투
사람이 쓰지 않는 상투 표현이 깔렸는가.
- "결론적으로 말씀드리자면", "핵심은 다음과 같습니다"
- "~라고 할 수 있습니다", "~인 셈입니다"의 반복
- 매 문단을 "또한", "따라서", "즉"으로 시작
- 요청하지 않은 요약 문단을 끝에 덧붙이기
- 사과와 겸양: "부족한 점이 있을 수 있습니다"
- 볼드 남용. 한 문단에 강조가 셋 이상이면 강조가 아니다

### 결론 실종
결론이 맨 뒤에 있는가. 배경 → 과정 → 결론 순서로 쓰면 읽는 사람은 끝까지 읽어야 한다.
보고와 요약은 결론이 첫 줄이다.

### 근거와 추정 뒤섞임
확인한 것과 짐작한 것이 같은 말투로 쓰였는가. 실측값과 추정을 구분하지 않으면 읽는
사람이 판단을 못 한다.

### 용어 흔들림
같은 개념이 문단마다 다른 단어로 불리는가. 반드시 표로 정리한다.

| 개념 | 발견된 표기 | 권장 표기 |
|---|---|---|

### 자작 압축 용어
설명 없이 만들어 쓴 줄임말이나 합성어가 있는가. "검수기", "동기화판", "재판정 루프"처럼
글쓴이만 아는 말은 처음 나올 때 풀어 쓰거나 원래 용어로 되돌린다.

### 벽글
한 문단이 6문장을 넘는가. 헤딩 없이 화면 한 장을 채우는가. 목록으로 쪼갤 내용이
문장 속에 가운뎃점으로 나열됐는가.

### 구분 기호 남용
하이픈, 엠대시, 콜론, 세미콜론이 문장 속 접속사로 쓰였는가. 가운뎃점이 문장 안에서
"그리고" 자리를 대신하는가. 메타데이터 줄의 나열용 가운뎃점은 정상이다.

### 표기 흔들림
- 숫자와 단위 띄어쓰기가 문서마다 다름: "3분" vs "3 분"
- 영문·한글 사이 띄어쓰기 불일치
- 날짜 형식 혼용: "9/8", "2026-09-08", "9월 8일"
- 파일 경로와 식별자가 백틱 없이 본문에 섞임

## 2. 말투

- 문서(md, README, 가이드, 설계, 회의록)는 **문서체** `~한다`가 기본이다
- 사람에게 하는 보고와 채팅 답변은 **보고체** `~합니다` 또는 사용자가 정한 말투다
- 한 문서 안에서 섞지 않는다. 종결어미를 정하고 끝까지 간다
- 화면 UI 문구는 반대다. 문서체 `~한다`를 화면에 쓰지 않는다(`ko-ui-text` 참고)
- 독자가 아는 것을 다시 설명하지 않는다. 이미 맥락을 아는 동료에게 배경 문단을 붙이지 않는다
- 사과하지 않는다. 잘못이 있으면 무엇이 틀렸고 어떻게 고쳤는지만 쓴다

## 3. 구조

- **두괄식**: 결론 한 줄이 먼저. 근거와 과정은 그 뒤
- 문단은 3~5문장. 한 문단에 한 가지
- 헤딩은 명사구. 15자 이내. 헤딩에 주장문이나 근거를 넣지 않는다
- 목록은 한 층에 6개까지. 넘으면 묶어서 층을 나눈다
- 목록 항목의 형태를 통일한다. 명사구로 시작했으면 끝까지 명사구
- 항목이 2차원(항목 × 속성)이면 목록이 아니라 표다
- 코드 블록에는 언어를 붙인다. 실행 결과는 별도 블록으로 분리한다
- 링크는 "여기"가 아니라 대상 이름으로 건다

## 4. 문장

- 한 문장에 한 가지. 60자를 넘으면 끊을 자리를 찾는다
- 주어를 생략할 때 주체가 모호해지면 살린다. 특히 "누가 했는가"가 중요한 보고에서
- 이중 부정은 긍정으로 바꾼다
- 수식어는 꾸미는 말 바로 앞에 둔다
- 같은 문장 안에서 시제를 섞지 않는다
- 문장 끝에 근거 없는 강조를 붙이지 않는다: "매우", "굉장히", "확실히"

## 5. 근거와 추정 구분

사실과 짐작을 어휘로 구분한다. 이게 문서의 신뢰를 만든다.

| 상태 | 쓰는 말 | 예 |
|---|---|---|
| 직접 확인 | "확인했다", "실측 결과" | "실측 결과 27/27 검출됐다" |
| 재현됨 | "재현된다" | "같은 순서로 세 번 재현된다" |
| 추정 | "~로 보인다", "추정한다" | "펌웨어 쪽 문제로 보인다" |
| 미확인 | "확인하지 못했다" | "원인은 아직 확인하지 못했다" |
| 남의 말 | 출처를 밝힌다 | "문서에는 48KB가 한도라고 적혀 있다" |

- 수치는 출처를 붙인다. 실측인지 문서값인지 계산값인지
- 실패한 것을 성공처럼 쓰지 않는다. 검증하지 않은 것을 검증했다고 쓰지 않는다

## 6. 영어 용어와 코드 식별자

- 기술 용어는 억지로 번역하지 않고 영어 원어를 그대로 쓴다: hook, worktree, pre-commit,
  commit, branch, merge, fork, rebase, cache, timeout
- 한글 음차는 피한다: "인트린식", "익스트린식" 대신 원어나 우리말 용어를 쓴다
- 굳어진 우리말이 있으면 그쪽을 쓴다: 저장소, 분기, 되돌리기가 이미 통하면 그대로
- 어느 쪽으로 정했든 문서 전체에서 고정한다. 용어집이 있으면 용어집이 이긴다
- 코드 식별자, 파일 경로, 명령어, 설정 키는 백틱으로 감싼다: `install.mjs`, `core.hooksPath`
- 약어는 처음 나올 때만 풀어 쓴다. 매번 병기하지 않는다

## 7. 숫자와 표기

- 숫자와 단위는 붙여 쓴다: 3분, 12.2초, 48KB, 30Hz
- 범위는 물결표: 3~5개. 빼기 기호와 섞지 않는다
- 날짜는 `YYYY-MM-DD`로 고정한다. "어제", "지난주" 같은 상대 표현은 문서에 남기지 않는다
- 증감은 방향을 명시한다: "12.2초에서 1.6초로 줄었다"
- 파일 경로를 사용자에게 보고할 때는 절대 경로를 쓴다. 문서 안에서는 상대 경로를 쓴다

## 8. 금지

- 하이픈, 엠대시, 콜론, 세미콜론으로 문장 잇기
- 가운뎃점을 문장 속 접속사로 쓰기 (메타데이터 나열은 예외)
- "X가 아니라 Y" 대조 구문의 반복
- 괄호로 부연 설명을 겹겹이 달기
- 슬로건 말투: "지금 바로", "새로운 기준", "~의 시작"
- 느낌표
- 이모지 (명시적 요청 외)
- 요청하지 않은 마무리 요약 문단
- 읽는 사람을 가르치는 말투: "~해야 한다는 점을 명심하자"

## 9. 판단이 애매하면

- 소리 내어 읽어서 걸리면 다시 쓴다
- 이 문장이 없어도 결론이 서는가. 서면 지운다
- 이 문단을 읽고 독자가 다음에 무엇을 할지 아는가
- 원문이 이미 읽히면 손대지 않는다. "유지"로 표기한다
- 용어집과 "더 자연스러운 표기"가 충돌하면 용어집이 이긴다
- 독자가 개발자면 코드 식별자와 약어 허용 범위를 넓힌다. 말투와 구조 규칙은 그대로다
